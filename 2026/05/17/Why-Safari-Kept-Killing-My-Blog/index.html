Why Safari Kept Killing My Blog

My blog's JOSS review post crashed on every iOS Safari visit. The page would load, freeze for a few seconds, then the tab would die and reload in a loop. This post traces the root cause through WebGL memory limits, WASM compilation pressure, and 60fps draw loops that Safari handles differently from Chrome.

The Symptom

A friend texted me a screenshot: my blog post on solve_nivp was killing their iPhone. The page would start loading, the textmode.js ASCII background would flicker on for about two seconds, then Safari would nuke the tab. Reload. Flicker. Die. Reload. An infinite loop of a browser giving up.

On desktop Chrome? Worked fine. On desktop Firefox? Fine. On my own Android phone in Chrome? Fine. Only Safari, and only on iOS.

I: The Architecture

What This Blog Runs

This site uses three render systems simultaneously on every page:

  1. textmode.js[1] — A WebGL2-based ASCII art renderer. It creates a full-viewport <canvas>, draws character glyphs into a texture atlas, and composites them at 60fps using custom GLSL shaders. This powers the whale animation background, gradient effects, page separators, and physics simulations.

  2. tikzjax[2] — A WebAssembly port of the TeX typesetting engine. It finds <script type="text/tikz"> tags in the DOM, compiles LaTeX to DVI via WASM, then converts DVI to SVG client-side. Each compilation loads a ~5MB WASM binary plus a core memory dump.

  3. tikzsim — My custom module that renders interactive ASCII physics simulations (bouncing balls, wave interference, chattering systems) into textmode.js’s canvas. Four of these run on the JOSS post.

On the JOSS review page specifically, the browser loads at once:

  • 1 WebGL2 canvas running at 60fps
  • 4 tikz SVG diagrams compiled from LaTeX via WASM
  • 4 tikzsim ASCII simulations
  • The full whale background with wave physics

The Draw Loop

Every frame, textmode.js runs this cycle internally:

  1. Clear the WebGL framebuffer
  2. For each cell in the grid: write glyph index, foreground colour, background colour into instanced buffers
  3. Issue a single draw call (instanced rendering)
  4. Call gl.readPixels() on the framebuffer to read back pixel data

Step 4 is the expensive one. It forces a GPU→CPU synchronous readback, stalling the pipeline until the GPU finishes rendering. On desktop GPUs this stall is measured in microseconds. On mobile GPUs sharing memory with the CPU, it blocks the main thread for milliseconds per frame.

II: Why Safari Specifically

iOS Memory Model

Every browser on iOS uses WebKit under the hood<span class=”hint–top hint–error hint–medium hint–rounded hint–bounce” aria-label=”Apple’s App Store Review Guidelines, section 2.5.6: “Apps that browse the web must use the appropriate WebKit framework and WebKit JavaScript.”
“>[3]. Apple enforces this via App Store policy; Chrome on iOS is just a skin over WebKit’s rendering engine. So “Safari crashes” really means “WebKit on iOS crashes,” and there is no escaping it by switching browsers on that platform.

WebKit on iOS enforces a per-tab memory ceiling around 300MB (varies by device generation, but iPhone 12 and below sit in this range). When a tab exceeds this, WebKit’s jetsam mechanism terminates the web process. The tab reloads automatically. If the page immediately re-triggers the same memory pressure on reload, you get the death loop.

The Three Killers

1. readPixels Allocation Pressure

textmode.js calls gl.readPixels() every frame. This allocates a fresh Uint8Array(width * height * 4) each time. On an iPhone 12 viewport (390×844 pixels):

$$390 \times 844 \times 4 = 1{,}316{,}640 \text{ bytes} \approx 1.3\text{MB per frame}$$

At 60fps, that is 78MB/s of short-lived typed array allocations. Chrome’s V8 handles this with generational GC that quickly reclaims young-generation buffers. Safari’s JavaScriptCore uses a different GC strategy for large typed arrays; it defers collection longer, allowing heap to grow before sweeping. Under memory pressure, JSC triggers a full GC pass which pauses the main thread for 50-200ms, causing visible frame drops and compounding the stall from readPixels itself.

2. WebGL Context Loss Without Recovery

When memory pressure exceeds thresholds, WebKit reclaims WebGL contexts. The browser fires a webglcontextlost event on the canvas, after which every WebGL call becomes a no-op or throws. textmode.js (v0.13.0) has zero handlers for this event. The draw loop continues calling tm.rect(), tm.char(), tm.push(), tm.pop() into a dead context 60 times per second. Depending on the internal error handling path, this either:

  • Accumulates error objects until memory runs out further, or
  • Triggers an unhandled exception that propagates up to a framework error boundary, or
  • Causes WebKit to flag the tab as unresponsive and terminate it

None of these paths lead anywhere good.

3. WASM + WebGL Memory Competition

tikzjax loads a 5MB WASM binary, decompresses a core memory dump, and instantiates a TeX engine in linear memory. Each of the 4 tikz diagrams compiles sequentially, peaking at 40-60MB per compilation. WebKit’s WASM implementation on iOS has a fixed 32-bit address space with stricter guard pages than Chrome’s implementation. The peak WASM memory plus the WebGL framebuffer (preserveDrawingBuffer: true means the GPU keeps the full framebuffer between frames) plus the per-frame readPixels allocations:

$$\underbrace{80\text{MB}}{\text{WebGL buffers}} + \underbrace{60\text{MB}}{\text{WASM peak}} + \underbrace{78\text{MB/s}}{\text{readPixels GC backlog}} + \underbrace{40\text{MB}}{\text{DOM + JS heap}} > 300\text{MB}$$

The page was doomed from the moment it started loading.

4. The Mobile Resize Loop (bonus)

iOS Safari hides and shows the address bar as you scroll. Each hide/show fires a resize event because window.innerHeight changes. If resize triggers a full canvas teardown and rebuild (as textmode.js’s windowResized callback did), each scroll gesture causes:

  • Canvas resize → new WebGL buffers allocated → old buffers GC’d → memory spike
  • All modules reinitialised → allocations spike
  • If this overlaps with tikzjax WASM compilation → OOM

This alone could trigger the crash independent of the other issues, since scrolling is the first thing a mobile user does.

III: The Fixes

Seven fixes applied in total, addressing each vector:

Fix A: Debounced Resize Handler

The windowResized callback now debounces with a 150ms timer. Multiple rapid resize events (from iOS address bar animation) collapse into a single reinitialisation:

150ms is chosen because iOS address bar animations complete in ~300ms; the debounce fires once after the animation settles rather than dozens of times during it.

Fix B: Incremental Element Tracking

The tikzsim module previously destroyed all simulation state on every markDirty() call and rebuilt from scratch. On scroll (which fires markDirty), this meant:

  • Query all .tikz-ascii elements
  • Parse all JSON configs fresh
  • Reconstruct all physics simulations from initial conditions

Now queryElements() does incremental matching: existing simulations whose DOM element is still present are preserved. Only new elements get initialised, detached ones get removed:

Fix C: Consolidated Script Load Order

Previously, tikzsim-module.js was injected separately by the hexo-tikzjax plugin. The whale-bg.js coordinator would sometimes execute before tikzsim loaded, causing TikzSimModule to be undefined during init. Now all scripts load in a guaranteed sequence from a single injector:

whale-bg.js runs last, guaranteed that all modules are defined.

Fix D: Pinned textmode.js Version

The CDN import was textmode.js@latest, which meant any upstream breaking change would silently propagate. This is now pinned to @0.13.0. I wasted two hours debugging a “regression” that turned out to be an upstream alpha release of 0.14.0 changing the shader compilation path.

Fix E: WebGL Context Loss Handler

The canvas now listens for context loss and suppresses the draw loop until recovery:

The e.preventDefault() is required; without it, WebKit will not attempt to restore the context. The draw loop checks contextLost before doing any work:

When the context is lost, the page still functions (text is readable, links work), you just lose the ASCII background animation until Safari decides to restore the context. Much better than a tab crash.

Fix F: Mobile Frame Skip (30fps)

On viewports below 768px, the draw loop now skips every other frame. This halves the readPixels allocation rate from 78MB/s to 39MB/s, giving the GC breathing room:

The ASCII animations are not fast enough to notice the difference at 30fps vs 60fps. The characters update slowly by design; halving the render rate saves half the GPU stalls and GC pressure with no visible quality loss.

Fix G: Lazy-Load tikzjax via IntersectionObserver

The most impactful fix. tikzjax.js previously loaded with defer, meaning it would start compiling WASM the moment the DOM was ready, racing with textmode.js for memory during the most allocation-intensive phase (initial canvas setup, texture atlas generation, first frame). Now it loads only when a tikz container scrolls within 300px of the viewport:

On the JOSS post, the tikz diagrams are below the fold. The user sees the page load, the whale animation start, reads the introduction, and only when they scroll toward the first diagram does tikzjax begin downloading and compiling. By then, textmode.js has already finished its heavy initialisation phase and settled into a steady-state memory usage. The two systems never compete for memory simultaneously.

The DOMContentLoaded wrapper is necessary because the loader script lives in <head>, which executes before any <script type="text/tikz"> elements exist in the body. Without it, querySelectorAll finds nothing and the observer is never created.

What I Learned

Safari is not broken; it is opinionated. WebKit on iOS enforces strict memory budgets because iPhones cannot swap to disk, there is no virtual memory paging, so the OS must kill processes that consume too much physical RAM. Chrome on desktop operates in an environment with 16GB+ of RAM and swap files. Chromium on Android has similar constraints to iOS but with larger per-process budgets and a more forgiving OOM killer.

The fixes boil down to one principle: spread memory usage over time instead of concentrating it at page load. Debounce resize so allocations don’t spike. Skip frames so GC can reclaim. Lazy-load WASM so it doesn’t compete with WebGL init. Handle context loss so the page degrades gracefully instead of dying.

If you are building anything with WebGL + WASM on the same page, test on an actual iPhone. Chromium with a mobile viewport and CPU throttling will catch performance issues but not memory limits. The iOS per-tab memory ceiling is a hard wall that no amount of optimisation can exceed; you have to restructure when things load relative to each other.
